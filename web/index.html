How it works

1

Read the bytecode

Paste any mainnet account. BitLens fetches the deployed WASM and reads its host imports, exported methods and token standards: can it send NEAR, add keys, redeploy itself, call other contracts?

2

Attack it in a local sim

The real bytecode runs in a local NEAR runtime (near-contract-sim) with an owner, a victim and an attacker: unauthorised admin calls, added keys, same-block double withdraws, failed-transfer refunds, callback out-of-gas, stale yield timeouts.

3

Get a verdict with evidence

Each defence comes back HELD, BROKEN or INCONCLUSIVE, with the receipt trail and who gained or lost NEAR, and you can replay the attack as an animation. If BitLens couldn't drive the contract, it says so instead of guessing.

Text-to-test: describe an attack, get a test

Type an attack in plain English. An LLM (NEAR AI Cloud, with OpenRouter as fallback) translates it into a scenario JSON for this contract. It never writes code. The JSON is validated (real methods only, fixed sim accounts, checks that must hold) and you can review or edit it before it runs on the same engine as the built-in attacks.

For AI agents

An MCP server: your agent checks before it signs

Before signing, the agent hands BitLens the transaction it is about to send. BitLens attacks the contract in a local simulator and answers allow, confirm or block, with the attack that proves it. BitLens never signs: the agent's wallet signs only on allow. Hosted MCP server over HTTPS (Streamable HTTP, bearer token), or self-hosted over stdio; every tool is read-only and validates its input.

check_transaction

Call it right before signing: allow / confirm / block, with the proof and a replay link.

scan_contract

Capability risk card from the bytecode. Instant.

list_attacks

The attack scenarios that apply, with their scenario JSON.

run_attacks

Runs them in the local sim: status, explanation, receipts, NEAR deltas.

assess_contract

Scan + all attacks → safe / caution / dangerous with reasons.

run_custom_attack

Your agent's own idea, in plain English or as scenario JSON.

Add it in one line

Claude Code (hosted, HTTPS)
claude mcp add --transport http bitlens https://bitlens-api.buoya.space/mcp --header "Authorization: Bearer <your-token>"
Any MCP client (Streamable HTTP)
{
  "mcpServers": {
    "bitlens": {
      "type": "http",
      "url": "https://bitlens-api.buoya.space/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}

The hosted server needs a bearer token: ask the BitLens team for one. Then claude mcp list shows bitlens … ✓ Connected.

Self-host instead (stdio, no token)
Claude Code, from a clone of the repo
claude mcp add bitlens -- "$PWD/node_modules/.bin/tsx" "$PWD/mcp/server.ts"
Claude Desktop / any MCP client (stdio)
{
  "mcpServers": {
    "bitlens": {
      "command": "/ABSOLUTE/PATH/TO/bitlens/node_modules/.bin/tsx",
      "args": ["/ABSOLUTE/PATH/TO/bitlens/mcp/server.ts"]
    }
  }
}

After npm install and npm run build:runner. Plain-English attacks need NEAR_AI_API_KEY or OPEN_ROUTER_KEY. You can also serve MCP over HTTP yourself: set BITLENS_MCP_TOKEN and run npm run server.
